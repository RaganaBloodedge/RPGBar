# Agent 能力审计

本审计按当前代码遍历 `server/`、`server/agents/`、`compiler/` 和 `web/`。原则是：

1. 模型负责理解、提议、生成语言和抽取语义；
2. 服务端负责权限、骰子、状态写入、路径安全和一致性；
3. 两者之间通过结构化 JSON、工具 schema 和校验器连接。

## 服务端模块

| 模块 | 当前职责 | 模型是否适合参与 | 建议形态 |
|---|---|---:|---|
| `agents/narrator.py` | DM 判断行动、调工具、写旁白 | 是 | 保留工具 Agent；把“行动意图/边界/检定选择”拆成模型提议 + 服务端校验 |
| `agents/advisor.py` | 玩家建议 | 是 | 保持只读；建议由当前场景和剧本动态生成 |
| `agents/persona.py` | NPC 人设、反应、摘要、角色卡 | 是 | 继续使用单轮 JSON + 严格校验 |
| `agents/tool_agent.py` | 多种固定任务引擎 | 是 | 作为统一任务运行时；增加 schema 版本与失败原因 |
| `state_machine.py` | 场景、flag、玩家和回合状态 | 否 | 必须确定性执行，模型只能提议变更 |
| `world.py` | 现场实体、地点、线索、时间 | 部分 | 地点理解可由模型提议；实体存在、死亡、移动必须服务端确认 |
| `dice.py` / `rules.py` | 骰子和判定 | 否 | 模型不能得到骰点，也不能传入结果 |
| `character_card.py` | 角色卡 schema 和点数校验 | 部分 | schema 可由模型生成；区间、点数和加值必须确定性校验 |
| `npc.py` | NPC 状态和反应采样 | 部分 | 人设/候选反应由模型提供，落点由服务端骰子决定 |
| `chronicle.py` | 叙事档案、摘要和时序检索 | 部分 | 摘要可由模型生成；写入、幂等、时间/场景/类型过滤和检索由服务端负责 |
| `rag.py` / `kb_tools.py` | 剧本和规则书检索 | 否 | 召回由 BM25/向量确定性执行，模型只解释召回内容 |
| `session_zero.py` | 故事圣经和开场生成 | 是 | 继续由模型生成，但产物必须过结构校验并落库 |
| `main.py` | 房间、权限、WebSocket、广播 | 否 | 不交给模型；可增加模型任务调度层，但不能让模型直接改权限 |
| `llm.py` / `llamacpp.py` | 模型通道和进程管理 | 否 | 保持基础设施层，不掺入剧情逻辑 |
| `lobby.py` | 房间参数和密码 | 否 | 完全确定性 |

| 模块 | 当前职责 | 模型可承担的部分 |
|---|---|---|
| `reader.py` / `layout.py` / `outline.py` | PDF 几何、阅读顺序、书签和区间 | 不应交给模型 |
| `segment.py` / `graph/llm_classify.py` | 五类分类和条目边界 | 已经是模型主判，规则层做护栏 |
| `extract.py` | 实体和字段抽取 | 适合拆成“实体发现 → 字段抽取”两段 Agent |
| `containers.py` | 规则、技能、物品、NPC、lore 容器化 | 模型负责命名/归类/摘要，投影和字段落库由代码完成 |
| `timeline.py` / `sandbox.py` | 从规则书生成可玩沙盒 | 高度适合模型，但场景图、出口、检定和引用必须结构校验 |

| `selfcheck.py` / `gate.py` | 编译验收和门禁 | 不应由模型决定是否通过 |
| `report_html.py` / `browse.py` | 报告和浏览 | 不需要模型 |

## 当前最值得增加的 Agent

### 1. 行动裁定 Agent

输入当前场景、现场实体、玩家原话，输出：

```json
{
  "intent": "fact_question|normal_action|check|move|blocked|meta|ambiguous",
  "target_check": "检定 id 或 null",
  "target_exit": "出口 id 或 null",
  "requires_refusal": false,
  "reason": "逐句解释"
}
```

服务端只接受当前场景中存在的检定和出口。这样可以逐步替代 `narrator.py` 中的固定越界词表。

### 2. 剧本边界 Agent

在编译剧本时，根据剧本内容生成：

- 可接受行动类型；
- 不应出现的现代物件、能力和地点；
- 每个场景的事实问句样例；
- 每个出口和检定的自然语言触发样例。

这些内容写入剧本的 `behavior_profile`，运行时只读取当前剧本自己的边界。

### 3. 场景一致性审查 Agent

每次模型准备广播前，检查：

- 是否引入了未登记的实体；
- 是否让已死亡/离开的 NPC 再次出现；
- 是否把失败写成成功；
- 是否泄露 `dm_notes`；
- 是否重复系统已经广播的事实。

它只能返回审查结果，不能直接改状态；最终是否接受由规则校验器决定。

### 4. 玩家测试生成 Agent

已加入 [`scripts/player_acceptance.py`](../scripts/player_acceptance.py)。它从当前剧本生成真实玩家语句和可观察验收条件，支持不同剧本自动产生不同测试集。

## 不应交给模型的功能

- 骰子和成功率；
- 房间权限、密码、踢人和转让；
- 场景状态和 flag 的最终写入；
- 角色卡数值边界；
- 文件路径和资源访问；
- 事件顺序和广播；
- 剧本编译是否通过；
- NPC 死亡、门是否存在、物品是否已经取得等强一致事实。

## 时序 RAG 验收结论

`Chronicle` 已经是可持久化的事件档案：每条记录带有 `turn`、`scene`、`kind`、`actors` 和写入时间，支持 BM25 与向量 RRF 检索。此前它只能按相关性召回，不能按剧情回合组合过滤，因此只能称为“带时间元数据的 RAG”。现在 `recall_history` 支持 `after_turn`、`before_turn`、`scene` 和 `kinds`，并且 actor 过滤会保留这些约束；对应验收脚本是 `scripts/temporal_rag_check.py`。

`WorldState` 仍然负责“当前是什么状态”，`Chronicle` 负责“之前发生过什么”。两者分层可以避免模型把历史叙述当成当前事实，也避免为了查询历史而修改世界状态。

## 结论

当前项目已经具备三类 Agent：DM、玩家助手、主机小助手。下一步不应继续给 DM 增加更多自然语言规则，而应增加“行动裁定 Agent”和“场景一致性审查 Agent”，把当前散落在正则、关键词表和旁白护栏里的语义判断，迁移为“模型理解 + 结构化结果 + 服务端校验”。

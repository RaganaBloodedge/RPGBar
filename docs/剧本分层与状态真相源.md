# 剧本分层与「状态真相源」（想法记录，2026-10-22，未设计完、未实施）

> 起点判断：**以现在的结构，长剧本必然驾驭不住。** 不是模型不够大，是「剧本」和「状态」
> 这两件事现在混在同一堆文本里，靠上下文窗口 + RAG 去兜，兜不住。

## 1. 现在的问题长什么样

当前一个剧本 = 一个 JSON（场景 / 出口 / 检定 / flags / NPC 卡），运行时：

- `scene_brief` 把当前场景压成一段文字塞进 prompt；
- RAG 检索剧本片段补充细节；
- `chronicle` 记「已发生事实」，`digest(n)` 摘最近几条。

三个结构性缺口：

1. **切分靠人肉**：新剧本进来没有编译/校验流程，写错了（场景不可达、flag 没来源）要到玩到那一步才发现。
2. **规则和世界观没有常驻位置**：它们散在场景描述里，重要的时候不一定在上下文里，不重要的时候又占着预算。
3. **状态没有真相源**：玩家做了什么、NPC 死没死、门开没开，全靠文本记忆 + 后来的模型自己「想起来」。

## 2. 一个剧本其实是三种东西

| 层 | 内容 | 性质 | 该放哪 |
|---|---|---|---|
| **世界观与规则** | 世界设定、冲突/判定规则、技能表、语气与禁则 | 静态、全局、永不变 | **常驻 system prompt**（硬预算） |
| **剧情** | 场景、事件、出口、推进条件 | 图结构，非文本 | 结构化存储，**只给当前节点邻域** |
| **角色/实体** | NPC 卡 + 当前状态（在场/死亡/敌对/离开） | 可变状态 | **结构化状态表**（真相源） |

关键：**「剧情」是图不是文章**。文章只能整篇给或整篇检索，图可以只走当前节点。

## 3. 为什么现在的 RAG 一定会翻车

用户举的例子最典型：

> 玩家突发奇想攻击某个 NPC，NPC 死了。后续剧情如果还要用到这个 NPC，系统必须知道「这个人已经不存在了」。

RAG 做不到，原因是**语义上的**，不是参数没调好：

- RAG 是**相似度召回**，不是**事实断言**。它回答「哪段文本像」，不回答「现在是什么状态」。
- 死亡这件事需要**强一致**：每轮都必须成立，不能靠「刚好召回得到」。
- 更糟的是召回反而帮倒忙：历史里有大量「卡特站在门口」「卡特说……」的文本，玩家问起卡特时，
  相似度最高的恰恰是这些**过时**的段落 —— 检索越准，越强化错误。

⇒ 必须把两类记忆分开：

- **可检索的叙事记忆**（chronicle：发生过什么、说了什么）—— 允许摘要、允许遗忘、允许召回失败；
- **必须强一致的实体状态**（谁活着、谁死了、门开没开、拿到了什么）—— 结构化、每轮全量注入、不允许靠检索。

## 4. 分层草案（L0–L3）

```
L0 规则层    世界观 + 判定规则 + 语气禁则       常驻 system prompt，硬预算（比如 ≤1200 tokens）
L1 状态层    当前场景 / 在场实体状态表 / flags   每轮注入，结构化，小（几十行）
L2 进度层    剧情图 + 当前节点 + 可达邻域骨架    每轮注入当前节点邻域，不注入全图
L3 记忆层    chronicle（叙事事实）              可检索 / 可摘要，允许退化
```

四个要点：

1. **L0 常驻**：规则和世界观永远在，不靠检索；超预算就压缩成纲要，细节按需下钻（规则查询单独工具）。
2. **L1 是真相源**：实体状态表里，死者保留**墓碑条目**（`dead`），注入时写明「已死亡，不得再出场」。
   这比「检索到死亡那段」可靠一万倍。
3. **L2 只给邻域**：当前场景的完整描述 + 出口 + 检定 + 直接可达的下一批场景的**骨架**（一句话 + 出口名）。
   长剧本的成本因此与「剧本总长」无关，只与「节点度」有关。
4. **写入顺序**：先落 L1（结构化事实），再落 L3（叙事文本）。反过来就会变成「文本说得对，状态不知道」。

## 5. 配套的两个机制（草案）

- **实体状态机 + 旁白护栏**：`alive / dead / gone / hostile`；模型不能直接改状态，只能经工具或判定改。
  旁白里若让已死实体作为行为主体出现 → 打回重写（跟越界动作护栏同一套思路：能结构化的别求小模型）。
- **剧本编译器**：导入新剧本 → 校验（每个场景可达、每个 flag 有来源也有消费、每个 NPC 有出场条件、
  规则段能装进 L0 预算）→ 产出结构化存储 + 一份「剧本清单」。写错在导入时报，不是玩到才报。

## 6. 开放问题（都还没答案，先记着）

1. **状态存哪** —— 跟「存储管理」那件事合并想（JSON / SQLite / 每房间一目录）。
2. **剧情图 vs 线性章** —— 蛇王墓这种单线够用；多线/开放世界要不要支持并行支线、回访、世界时间推进？
3. **作者格式** —— 剧本作者（可能是我自己）写什么格式最省事：现在的 JSON 扩展？还是「场景 md + 规则 md」再编译？
4. **L0 预算怎么定** —— 固定 token 数还是按总上下文比例？规则超了怎么摘要而不失真？
5. **RAG 还留不留** —— 我的判断：留，但降级为「细节回忆 + 规则查询」，不再承担状态和推进。
6. **现有 `totsk_l1.json` 迁移成本** —— 9 场景 12 flags 是个合适的第一块试验田。
7. **和长模拟测试的关系** —— 测试方案（`docs/长模拟测试方案.md`）暂停；等这套结构定了，
   断言层的检查对象会从「旁白文本」转向「状态表变化」，反而更好测。

## 7. 一句话总结

**规则常驻、剧情走图、状态做表、叙事才检索。** 现在的结构缺的正是中间两层（状态表 + 剧情图），
所以只能拿 RAG 硬撑，撑不住长剧本。

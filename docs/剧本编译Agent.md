# 剧本编译 Agent：把规则书编译成「可查询的知识库 + 可推进的时间线」

> 2026-10-22。针对「跑团游戏自由度太高、没有固定剧本、只有一本规则书」这件事，
> 把 `docs/剧本分层与状态真相源.md` 里的草案落成一条可复跑的编译流水线。
> 首个语料：《克苏鲁的呼唤 第七版》守秘人规则书，418 页，2 栏排版，176 条书签，110 张表。
>
> 代码在 `compiler/`，产物在 `data/kb/coc7e/`（`kb.sqlite` + `layout_profile.json` + `report.json`）。

---

## 0. 一句话结论

**规则书不能靠"检索"用，只能靠"编译"用。**

编译期把「一本书」变成三样东西：**结构（章节树/块）+ 数据（实体/字段/事实）+ 图（规则流程/剧情场景）**；
运行期 DM 只做三件事：**按名字取卡、按语义取原文、按状态取真相**。

其中最关键的一条设计约束是用户提的：**不要预设表结构**。
所以整套存储是「实体 + 事实键值 + 字段字典」，字段由 Agent 读到什么就长什么。

---

## 1. 为什么现在的 RAG 一定不够用

不是参数没调好，是**问题类型不对**。三种失败模式，在这本书上都能复现：

| 失败 | 现象 | 根因 |
|---|---|---|
| 切在句子中间 | 一条技能的描述被切成两半，前半段挂在上一页末尾 | 按页/按字数切，不知道"条目边界"在哪 |
| 召回到过时文本 | 玩家问"这个 NPC 还能说话吗"，召回的是他死之前那段对话 | 相似度召回不等于事实断言 |
| 查得到但用不了 | 搜到 8 段"战斗"相关文字，没有一段告诉你"先比 DEX 排顺序，再选近战/射击" | 规则是**流程**，不是**段落** |
| 字段被拍平 | "HP 14 / 护甲 2 / 移动 5"混在一段话里，模型每次都要重新解析 | 没有结构化抽取，只有文本 |

结论：**RAG 只解决"找到相似的文字"，而 DM 需要的是"拿到正确的值"和"按流程走一遍"。**
两者之间差一层编译。

## 2. 总体架构：编译期 / 运行期彻底分开

```
                  ┌──────────────── 编译期（离线，一本书跑一次）────────────────┐
  PDF ──► S0 读入 ──► S1 版式画像 ──► S2 粗分 ──► S3 细分 ──► S4 五类归类
                        ★统一范式      章节树       块          五大类+子类
                                                              │
                    S8 自检 ◄── S7 索引 ◄── S6 建图 ◄── S5 抽取（字段自动拓展★）
                       报告        BM25+向量    流程/引用/场景   实体+事实+字段
                  └──────────────────────────────────────────────────────────┘
                                          │
                                    kb.sqlite（只读知识 + 可写状态）
                                          │
                  ┌──────────────── 运行期（每轮）────────────────┐
                  │  DM：kb_search / kb_item / kb_skill / kb_npc  │
                  │      kb_rule+flow / kb_state / kb_progress     │
                  └───────────────────────────────────────────────┘
```

两条轴必须正交，这是整套设计的地基：

- **知识轴（静态）**：这块文本是什么类别 → 可以全量索引、随便检索、永远不变。
- **时间轴（动态）**：故事走到哪、谁死了、门开了 → 必须强一致、只追加、每轮全量注入。

把这两件事混在一张表里，就会出现"检索越准，错得越狠"。

## 3. ★ 摸清版式：统一范式（`compiler/layout.py`）

这是整个方案里最需要"通用"的一层。不同文档类型（规则书 / 小说 / 技术手册 / 论文 / 扫描件）
的结构信号完全不同，如果把"这行是不是标题"的判断散落在抽取器里，每接一本书就要改一遍抽取器。

所以把它抽成一个独立阶段，固定四步：

```
1. 证据       书签？目录页？字号直方图？缩进直方图？表格网格？文字层质量？
2. 假设       若干"标题家族"：第X章 / 1.2.3 / Chapter N / 全大写 / 纯字号聚类
3. 打分       有书签 ⇒ 用书签算召回（免费标注集）；没书签 ⇒ 用自洽性打分
4. 定策       选主策略 + 后备链，连证据一起写进 layout_profile.json
```

### 3.1 为什么"书签是校准器，不是靠山"

这本 COC 规则书自带 176 条书签（1 级 21 / 2 级 115 / 3 级 40）。天真做法是直接用书签切章 ——
能跑，但换一本没有书签的书就全废。

正确用法是：**把书签当标注集，用来验证"我认标题认得准不准"**。

```
font_cluster  = 0.773（命中 257）   ← 主策略
cjk_chapter   = 0.701（命中 21）
arabic_dotted = 0.655（命中 111）
table_caption = 0.651（命中 27）
```

打分公式（`_score_family`）：

- 有书签：`recall` = 书签里有几条能在"它标注的那一页"上被这个家族认出来（标题相似度 ≥0.62）；
- 没书签：`consistency` = 命中行里"短行 + 不是句子结尾"的比例 ×（1 − 噪声惩罚）；
- 都乘 `min(1, hits/8)`：只命中 1 次的家族不该拿高分（否则一个巧合就能当主策略）。

于是同一套代码：有书签的书 → 置信度 0.887；没书签但有目录页的书 → 置信度 ~0.7；两者都没有 → 0.5 并告警。

### 3.2 类型判定只影响先验和告警，不影响能不能跑通

`doc_kind ∈ {rulebook, novel, manual, academic, scanned, generic}`。
判定依据是"每页字数 + 骰子行比例 + 表格数 + 结构词"这类可测量的量，而不是猜。

**扫描件**（每页 <120 字、50% 页面近乎空白）会被直接判成 `scanned`、置信度压到 0.2、并明确告警
「需要 OCR」—— 假装能编译比报错更糟。

### 3.3 页眉页脚：不按比例，按"重复"

固定比例（页面高度 7%）在这本书上会直接把正文第一行切掉（页眉 y=30、正文 y=53，7% × 842 = 59）。
改成**按重复统计**：同一串文字在 20+ 页的同一位置出现，它就是页眉/页脚。

实测输出：`页眉带 36pt：CallofCthulhu7thEdition(199页)、第十四章怪物…(37页)、第十五章模组(21页)`。

### 3.4 换一种文档要改什么

| 场景 | 要动的 | 不要动的 |
|---|---|---|
| 同类型另一本规则书 | 什么都不用改 | 全部 |
| 无书签的扫描转文字版 | `layout.FAMILIES` 里加一个家族（比如题号 `^[一二三]、`） | 抽取器、存储、检索 |
| 小说（无编号章） | 加 `font_cluster` 权重或 `all_caps` 家族 | 同上 |
| 技术手册（1.2.3 编号） | 已经有 `arabic_dotted`，跑 `profile` 看打分即可 | 同上 |
| 真扫描件（无文字层） | 前置 OCR，其余不变 | 同上 |

`python -m compiler.cli profile --pdf 新书.pdf` 就是干这个的：**先摸底，再决定要不要加家族**。

## 4. 粗分与细分：不按页切

### 4.1 粗分（`outline.build_sections`）

三种来源按可信度排序：**书签 > 目录页反解 > 版式标题**。
目录页反解要处理一个所有人都踩的坑：目录上印的是「印刷页码」，PDF 里是「页序号」。
这本书的偏移是 **8**（PDF 第 9 页 = 印刷第 1 页），`_detect_page_offset` 用页脚数字的众数算出来。

产物是 176 个 section，带 `page_start/page_end/parent_id/path`，
`path` 形如 `第六章 战斗 > 6.2 常规接触战斗` —— DM 引用出处时直接可用。

### 4.2 细分（`outline.split_blocks`）

**按段落边界切，不按页切。** 判据只有三条：换页、行距变大、行首缩进变化（首行缩进 vs 顶格续行）。

两个踩过的坑，都写进注释了：

1. **双栏阅读顺序**：PDF 里行按 y 排，左栏第 1 行和右栏第 1 行 y 相同。按 (y,x) 排会把两栏
   **逐行交替**拼起来 —— 实测拼出「潜水（01%） 机械维修（10%）」这种把两条技能缝在一起的鬼东西。
   解法：先分栏（栏首间距 >150pt 才算换栏），再"一栏读到底"。
2. **跨栏续行**：一个段落在左栏没写完，句子在右栏顶部接着写。按"换栏=新段"会把一句话劈成两半。
   解法：换栏时看一眼"上一行有没有句末标点 + 新栏第一行是不是该栏的续行位置"。

### 4.3 条目头：块的基本单位

COC 的技能（`考古学（01%）`）、法术（`束缚术`）、怪物（`拜亚基，星骏`）都是同一形态：
**单行、短（≤30 字）、不带句末标点**。这条规则把 4.6 技能列表切成 50 块，一块一条技能。

**不能用缩进判断** —— 实测这本书里条目名和它的说明段起始 x 相同（都是 58pt），靠缩进会把 100 条技能缝成一条。

### 4.4 表格：自己算，不用 `find_tables`

PyMuPDF 的 `find_tables` 在这本书上有两个问题：整本遍历会中途段错误（2.0 版），且只认有框线的网格。
所以用「词坐标聚类」自己判，关键的一步是 **列位置由数据行统计出来，不由表头**：

- 表头常被合并单元格、或被旁边栏的同一 y 的正文污染（实测表头里出现过「实验室里，等待不知情的科学家…」）；
- 数据行的单元格 x 位置重复出现（≥55% 行）才算一列；
- 表头那一行的**词**再贴到最近的列上，被合并的表头因此能拆开。

### 4.5★ 第三类版式：清单（不是段落，也不是表格）

规则书里有一类内容既不是段落、也没有表格列头，而是**清单**：

```
男装
精纺毛料礼服，$17.95
开司米礼服，$18.50
风衣，$9.95-35.00
```

第一版把它当段落，而段落合并是 `"".join`（中文行之间没有空格），于是**几十个商品被粘成
1000 字一坨** —— 就是"各种商品的价格为什么像没切过"的真正原因。

现在把它当第三类版式（`outline._find_list_runs / parse_list_line`）：

- **判据**：连续 ≥3 行都匹配 `名称，价格`（价格侧认 `$17.95`、`69 美分`、`$9.95-35.00`）；
  连续 3 行才成立，避免正文里偶然一句"…，$5"把段落切碎；
- **切法**：**一行一块**，`title` 就是商品名 —— 这样 `kb_item("开司米礼服")` 才能直接查到；
- **归类**：块自报 `kind=tool`（清单自带类别，不再靠词频投票）；
- **分类名**：往回找最近一条"不是条目、也不含价格"的短行（`男装` / `医疗用品` / `梳妆用品`），
  记进 `meta.group`；
- **抽取**：`extract_price_items` 把 `名称 + 价格 + 分组` 落成 item 实体与 fact。

实测这本书命中 512 行、全在物价表 7 页，别处零误伤；切完物价表 7 页从 9 块变成 463 块。

### 4.5 表格要摊平后再进"原文流"

抽取器拿到的不该是 PDF 的栏列，而是这种形状：

```
属性 | 平均 | 掷骰
STR | 90 | （5D6×5）
CON | 50 | （3D6×5）
```

`extract.build_stream()` 做这件事：按栏读、表格摊平、每个字符偏移都能回溯到页码。
这一步之后，怪物属性抽取就是三行正则的事。

## 5. 五大类与「子类自生长」（`compiler/classify.py`）

判定顺序是"**先看这本书怎么排的，再看这一块写了什么**"：

1. **章节先验（权重 5）**：第四章"技能"整章都是玩家属性类，第六章"战斗"整章都是规则类。
   一页有 100 个词，靠词频投票会把"战斗"章里的怪物数据投成 NPC 类，而章节先验几乎不会错。
2. **词汇特征（封顶 9×0.45）**：检定/难度等级/奖励骰……（规则）、属性/技能点/角色卡……（玩家）、
   价格/武器/载具……（工具）、护甲/理智损失/特殊能力……（NPC）、神话/历史/典籍……（世界观）。
3. **版式签名（最硬）**：表头"名称+伤害/价格" → 工具类；"STR/CON/SIZ + 平均/掷骰" → NPC 类。

**子类不是写死的枚举**，而是从内容里读：

- 规则类：先看正文命中了哪个领域词（战斗/追逐/理智/魔法/射击/毒/老化…，`RULE_DOMAINS`），
  再退化成章节标题。读到没见过的领域词，就是并排新增一个子类 —— 这正是
  「每当出现一个新的类似规则的类就添加为一个并行的子类」的实现方式。
- 实体类型同样会生长：`schema.register_etype("spell", …)`，`etypes` 记在 meta 里。

实测分布：`tool 897 / lore 445 / rule 390 / pc 233 / npc 216`（2181 块）。

## 5.5 正文规范：分类的硬约束（`compiler/spec.py`）

分类不能是"给模型一段文本问它属于哪类"——它会给出一个听起来合理的答案，哪怕这段根本不属于
五类里的任何一种。**没有边界约束的分类，等于没有分类。** 所以先立规范，再谈归类。

规范是单一真相源：**规则分类器按它判、LLM 按它答、报告按它验**，三处用同一份，
不会出现"提示词里写一套、代码里判另一套"的漂移。

每类写死四件事：

| 类别 | 块边界 | 证据（至少一条） | 必须产出 |
|---|---|---|---|
| `rule` 规则类 | 一条规则/一个判定点一块 | 判定词（检定/掷骰/难度/奖励骰）· 编号步骤 · 骰子表达式 · 章节归属 | rule 实体 + 原文 + 子类 + 可选流程图 |
| `pc` 玩家属性类 | 只描述角色自身 | 属性/技能点/职业/角色卡 · 章节归属（创建调查员/技能） | pc 字段 + 技能实体 |
| `tool` 工具类 | **一行/一物一块**，名字即索引 | 清单行/表格行 · 价格/射程/弹数 · 章节归属（物价/装备） | item 实体（名称唯一）+ 列名字段 |
| `npc` NPC 类 | **一只一块**（名字+属性块+能力） | 属性块（STR/CON…+平均/掷骰）· 护甲/理智损失/特殊能力 · 章节归属 | npc/monster 实体（只读）+ 属性/能力字段 |
| `lore` 常识世界观类 | 一个主题一块，相似主题合并 | 神话/历史/典籍 等设定词 · **叙述性段落**（句读密度）· 章节归属 | lore 实体（摘要+原文+补充原文） |

补充两点，都是实测逼出来的：

1. **证据有三类，结构证据与文本证据等价**：关键词、版式签名（清单行/表格行/属性块）、
   **归属证据**（"创建调查员"章里的短段落就是玩家属性类，哪怕它一个关键词都没有）。
   只认关键词会把章首导语全部判成"未分类"。
2. **允许 `unclassified`**：五类都过不了就留空，进报告等复核。**猜错比留空更糟** ——
   留空至少知道自己不知道。

### 归类流程（候选必须"过审"）

```
打分 → 候选按分数排序 → 逐条 spec.validate() → 第一个通过的才算
                          ↓ 全部不通过
                      unclassified（记下每个候选被拒的原因）
```

于是"分数高但不合规范"的候选会被跳过。实测这一条纠正了一批真实错误：
`伤害加值表` 的行（`STR：2-64`）原本因为含 `STR` 被判成 NPC/物品，规范里
"tool 禁止含属性块""npc 必须有属性块或能力块"把它挡了下来，最终按章节归属落到规则/玩家属性。

### LLM 契约（同一份规范）

`spec.build_prompt()` 把规范全文 + 待判文本 + JSON Schema 一起给模型；`spec.check_llm_verdict()`
按三条硬规矩验收：

- **类别必须在枚举内**（含 `unclassified`）；
- **`evidence` 必须能逐字在原文里找到** —— 编造的证据对不上原文，直接判废；
- 通过 `validate()` 的边界检查。
任何一条不过 → 降级为 `unclassified`，**不帮模型圆场**（圆场正是分类漂移的来源）。

```bash
python -m compiler.cli spec --kb data/kb/coc7e                 # 打印规范全文
python -m compiler.cli spec --kb data/kb/coc7e --prompt-for 260  # 看给 LLM 的提示词长什么样
```

实测：2181 块全部按规范复核，**合规率 100%**，`unclassified` 15 块（0.7%）——
它们在报告里列出页码与标题，等 LLM 复核或人工定夺，不混进五类。

## 6. ★ 开放模式存储：不预设表结构（`compiler/db.py` + `schema_skill.py`）

### 6.1 三层

```
entity   实体      "拜亚基" 是一只 monster，"考古学" 是一个 skill
fact     事实      (实体, 字段, 值) —— 值永远带原文引用与页码
field    字段字典   "护甲" 是什么意思、什么类型、什么单位、第一次在哪出现
```

为什么不用固定表（attribute 表里写死 STR/CON/SIZ/HP）：

- 规则书之间字段就不一样（COC 有 SAN，别的系统有"道行""灵力"）；
- 同一本书里字段也不一样（这只怪物有"护甲"，那只没有；这张表有"故障值"，那张没有）；
- 写死的代价是**每接一本书就动一次数据库迁移**，或者塞进 JSON 假装结构化。

`field` 表是这一层的核心：**它是 Agent 的产出，不是开发者的设计**。
字段第一次出现时，`schema_skill.observe()` 现场注册一条，带三样东西：

| 字段 | 例（"护甲"） |
|---|---|
| `key` | `monster.护甲` |
| `kind` | `num`（由值 `2` 推出的，不是由标签猜的） |
| `evidence_quote` | `护甲：2`（原文那一句 = 字段的出生证明） |
| `first_page` | `261` |
| `origin` | `label_line`（来自"标签：值"行，而非表头，置信度 0.85） |

### 6.2 三条硬规矩

1. **无证据不立字段**。没有 `evidence_quote` 的字段等于模型编的，宁可不要。
2. **同义合并优先于新增**。`价格 / 花费 / 售价 / 价格($)` 是同一列，合并只改 `aliases`，
   不动已写入的 fact。`SYNONYMS` 只是合并规则，不是字段清单 —— 没在表里的字段照样能长出来。
3. **类型靠值推，不靠标签猜**。看到 `1D6+1` 才知道是 `dice`，看到 `95` 才知道是 `num`，
   看到 `稀/CP/C` 才知道是 `enum`，看到 `见 6.6` 才知道是 `ref`。
   还会**改主意**：先见到"见6.6"记成 text，后面见到"1D6"就修正成 dice（记一条 `kind_fix`）。

### 6.3 于是"角色卡长什么样"这个问题消失了

卡片不用预先定义列，就是**该实体在某 scope 下的全部 fact**，按"字段从哪来"分三组：

```
structured  来自表格表头（最可信）   STR=90  CON=50  SIZ=90  DEX=67 …
labelled    来自"标签：值"行         HP=14  伤害加成=1D6  体格=2  移动=5/16 飞行
inline      来自正文内嵌            消耗=5 点POW  施法用时=1 小时
```

新书多一个"灵力"字段，卡片上自动多一行，**一行代码都不用改**。

### 6.4 字段字典是怎么长出来的（实测）

书的原件里没有任何"字段表"，这 185 个字段全是读出来的：

| scope | 字段数 | 说明 |
|---|---|---|
| `item` | 121 | 武器表 8 列、载具表、护甲表、物价表、典籍表……每张表的表头各长一批 |
| `monster` | 49 | STR/CON/SIZ/DEX/INT/POW + HP/护甲/伤害加成/体格/魔法值/移动/特殊能力 |
| `spell` | 7 | 消耗/施法用时/别名/理智损失…… |
| `skill` | 3 | 基础值/描述/对抗技能 |
| `lore` | 2 | 摘要/原文（合并时再加"补充原文"） |

审计流 `schema_log` 里能逐条复盘：`new`（新增）/ `alias`（并入别名，48 次）/ `kind_fix`（类型修正）/ `new_etype`。

## 6.5 原文层：**原始文本必须留着**

第一版把书切完就直接抽成实体/事实，原文散在 `block.text` 里、跨块的话就拼不回来了 ——
这等于"只留了解析结果，没留原文"，校对、复核、出错回查全都无从下手。补一层：

```sql
source_page(book_id, page, chars, text)   -- 逐页原样文本（阅读顺序，不摊平表格）
block.src_page / src_start / src_end      -- 每块指回原文的字符区间
```

三条用法：

- `python -m compiler.cli raw --page 260` —— 看某页原文（人读的顺序，不是 PDF 内部的行序）；
- `python -m compiler.cli raw --grep 1901` —— 在原文层里搜，返回页码与上下文；
- `python -m compiler.cli export --out 全文.md` —— 导出人读版全文，用于校对；
- `python -m compiler.cli browse` —— 生成 `browse.html`：**切分后的块逐条平铺**（标题/类别/页码/原文区间/正文），
  带类别筛选与搜索，页面底部附整页原文，点页码可跳过去对照"块切得对不对"。

**原文层只存游戏内容页**（398/418 页）。非游戏内容页一个字都不进库，只留一条拦截台账。

## 6.6 非游戏内容闸门：**强约束，不是关键词过滤**

第一版把版权页（"© 1981-2014 Chaosium Inc. 保留所有权利"）、译者名单（Achronidas / lsr /
飙车致死法厄同…）、目录、更新历史全当成"世界观"抽进了库。DM 查"神话"会先撞到版权声明。

现在做成三条硬机制（`compiler/gate.py`）：

1. **单一写入口 + fail-closed**：知识层只能经 `_write_blocks` / `_run_extractors` 写入，
   两者入口都先过 `judge_*`；判不准就拒。拒掉的东西进 `non_game_log`（页码 + 理由 + 内容指纹），
   **不留正文** —— 这就是"非游戏内容不放进本地存储"的字面实现。
2. **三层判定，粒度从粗到细**：
   - **结构层**（最硬）：书签/目录里标题是 目录 / 使用说明 / 前言 / 译者 / 版权 / 更新历史 /
     中文化进度表 / 译名表 → 整节拒；
   - **页级**：短页命中版权特征（©、注册商标、ISBN、禁止商业用途）→ 整页拒；
     名单页（≥8 行纯人名、无表格、无句读、页面短）→ 整页拒；整页链接堆砌 → 整页拒；
   - **行级**：署名行（`译/xxx`）、译者注（`译注：…`）、段内署名句（`…由 Achronidas 翻译。`）
     → 只删那一行/那一句，保留同段规则正文。**这一步是必须的**：这本书的译者名单印在
     第十章章首页，整页拒绝会把整章正文一起毙掉。
3. **事后断言**：编译结束在 `block.text / entity.name / fact.raw` 上反查版权与网址特征，
   命中数必须为 0，写在 `report.json → gate.violations`。约束因此是**可验证**的，不是口头约定。

判定必须谨慎的两处（都是实测踩出来的）：

- **有表格的页不判名单**：典籍表、载具表、法术表也是"一列短词"，按名单规则会把
  p216（神话典籍）、p130（载具表）整页误杀；
- **网址不是罪名**：p166 讲"怎么找到跑团伙伴"，1600 字里两个网址，整页毙掉就丢了一整页真内容。
  只有"短页 + 一堆链接"才算。

实测结果：拒 6 节 / 20 页 / 4 块；行级擦除 170 行（`credits_line`）；原文层 398 页 / 54.2 万字；
知识层里 `©`、`Chaosium Inc`、译者名单、`译注` 残留 **0** 处。

## 7. 检索契约：DM 只需要七个工具（`compiler/retrieve.py`）

| 工具 | 走哪条路 | 为什么 |
|---|---|---|
| `kb_item(name)` | 名字索引（精确 + 别名） | 玩家说得出名字时，语义检索是多余的，还会召回同名无关段落 |
| `kb_skill(name)` | 名字索引 | 同上；技能要的是"基础值 + 描述 + 对抗技能" |
| `kb_npc(name)` | 名字索引（只读） | 怪物卡必须稳定，不能被检索抖出别的版本 |
| `kb_rule(name)` + `flow` | 规则实体 + 流程图 | 规则要的是"步骤与分支"，不是"最像的一段话" |
| `kb_search(q, kind?, year?)` | BM25 + 向量混合 | 玩家用自然语言描述时才需要模糊匹配 |
| `kb_state(campaign, entity)` | 状态表（真相源） | **状态以这里为准，不要相信检索到的旧文本** |
| `kb_progress(campaign)` | 时间线游标 | 推进到哪、下一步哪些场景可走 |

**所有工具都返回原文**（`block.text`），摘要只当钩子（`block.summary`）。
向量是**可选**的（`bge-small-zh-v1.5` ONNX，拿不到就纯 BM25），因为主路径本来就是精确名 + 字面。

分数：`0.6 × 归一化 BM25 + 0.4 × 余弦`，标题命中再 +0.25。

### 时间过滤（"时间 RAG"的一半）

每个块带 `valid_from / valid_to`（世界时间区间，从正文里的年份读出来；读不到 = 超时间）。
`search(..., year=1925)` 只返回时间窗覆盖 1925 的块。

这解决的是「召回越准越强化错误」：问到 1925 年的水库，不会召回 1920 年的旧描述。

## 8. 时间线与进度：知识分类之外的第二根轴（`compiler/timeline.py`）

```sql
campaign(id, book_id, current_section, current_page, world_time, cursor)
timeline_event(campaign_id, seq, kind, title, body, block_id, page, world_time, payload, irreversible)
entity_state(campaign_id, entity_id, status, fields, updated_seq)
```

三个要点：

1. **实体在书里的定义是只读的**（`entity.readonly=1`），在**这一局**里的状态是可变的（`entity_state`）。
   玩家一枪打死 NPC，改的是 `entity_state`，不是书。
2. **只追加**：`timeline_event` 从不修改，能回放。`irreversible` 标记不可逆事件（死亡/失败）。
3. **墓碑优于检索**：死者保留一条 `status=dead` 的状态行。这比"检索到死亡那段"可靠一万倍。

场景从"模组"章的块里取（`s.path LIKE '%模组%'`），不预设剧本格式 ——
规则书也有模组章（第十五章：《古茂密林之中》《猩红文档》），换成本子也是同一条路。

### 8.1 「常识」和「世界线」分别落在哪（查库时的地图）

这两样东西经常被混为一谈，实际是两层、四张表：

| 你要找的 | 在哪 | 怎么看 |
|---|---|---|
| **常识与世界观**（神话、历史、地点、叙事技巧） | `entity(etype='lore')` + `fact(scope='lore')`，每条含「摘要 / 原文 / 补充原文」 | `python -m compiler.cli lore --kb data/kb/coc7e` |
| **世界线的静态骨架**（有哪些场景节点、按什么页序） | `block` 里剧情章的块（`story` 命令列出的那一串） | `python -m compiler.cli story --kb data/kb/coc7e` |
| **世界线的动态进度**（走到哪、发生过什么） | `campaign`（游标）+ `timeline_event`（只追加事件流） | `python -m compiler.cli timeline --kb … --start 试玩 --advance` |
| **谁死了/门开了** | `entity_state`（真相源，`status=dead` 留墓碑） | `timeline` 输出末尾「状态真相源」那一行 |
| **检索时的时间过滤** | `block.valid_from / valid_to`（61 块有世界年份） | `select page,valid_from,title from block where valid_from is not null` |

一句话记法：**常识 = 知识轴上的 lore（可检索、可摘要、可合并）；世界线 = 时间轴上的
campaign + timeline_event + entity_state（只追加、强一致）**。`valid_from/to` 是横跨两者的
那座桥 —— 它让"检索"知道"这条知识在哪个年代成立"。

三个已记录的坑（都写进代码注释了）：

- **lore 桶曾经是个垃圾桶**：`classify` 在分不出类别时兜底成 lore，结果"目录""使用说明"
  "引文出处""译/七宫涟"全进了世界观（103 条）。现在加了四道过滤（前言类标题、署名/标签行、
  被截断的书名、纯拉丁行），并给实体加了 `subtype`（世界观/神话/历史/典籍/叙事技巧/剧情），
  降到 65 条。
- **合并逻辑比错了对象**：早先拿"新块正文"和"已有摘要"算相似度，量纲不一致，永远比不中，
  同一段话被存成三个 topic。改成正文对正文之后才有真正的合并。
- **时间窗仍会被版权年污染**：`valid_from` 取"出现次数最多的年份"，并排除"XXXX 年版"、
  跳过前言/目录/译名表，但版权页和引文页仍可能带出版年（实测 p3 = 2013、p9 = 1937）。
  规则应该只认"模组/世界观正文"里的年份，这条还没做。

## 9. 实测（418 页 COC 规则书）

```
读入 2.7s / 画像 0.4s / 切分+归类 ~1s / 抽取 ~4s / 索引 ~5s      合计 12.3s
170 章节 · 2181 块 · 992 实体 · 174 字段 · 4569 事实 · 398 页原文 · 30 引用边
分类：rule 272 / lore 251 / npc 204 / pc 133 / tool 81
实体：item 736 / rule 135 / skill 87 / lore 62 / spell 20 / monster 18 / attribute 8
质量：28 页无块（多为插图页/空白页）· 可疑块 24（跨页断句）· 低置信块 2
```

抽查（`python -m compiler.cli demo --kb data/kb/coc7e`）：

- `kb_item("燧发手枪")` → p390，伤害 `1D6+1`、射程 `10`、每轮 `1/4`、价格
- `kb_skill("考古学")` → p45，基础值 `01%`、描述、对抗技能
- `kb_npc("拜亚基")` → p260，24 个字段：`STR 90 / CON 50 / SIZ 90 / DEX 67 / INT 50 / POW 50 /
  HP 14 / 伤害加成 1D6 / 体格 2 / 平均魔法值 10 / 移动 5/16 飞行 / 特殊能力…`
- `kb_rule("战斗轮")` → p88 + 流程图（3 节点 1 边）
- `kb_search("被怪物吓到精神崩溃会怎么样")` → 命中第十/八章关于疯狂与恐惧的段落

### 已知缺陷（诚实清单）

| 缺陷 | 影响 | 修法 |
|---|---|---|
| 怪物只抽到 18 只（第十四章实际 60+） | NPC 覆盖不足 | 有些怪物的属性块不是 3 列表（单栏/两列/无"掷骰"列），需要第二种锚点；或加 LLM 复核 |
| 物品价格偶有错列（`价格=1`，实际 `30/300`） | 少量物品字段错位 | 表头列名被合并时按词贴列会错位，需按行内 x 与表头列距离二次校正 |
| 规则流程图只抽到 7 条 | 大部分规则没有流程 | 现在只认编号步骤；应加"判定分支句式"识别 + LLM 复核 |
| 24 个块尾句不完整（跨页断句） | 检索片段读起来断头 | 用块尾无句末标点 + 下一页首行做续接 |
| 技能描述偶有 `|` 残留 | 个别描述脏 | 摊平表格与条目边界冲突，需在流里标记表格区间 |
| 闸门是规则式，没上模型 | 个别夹在长段落里的译者注可能漏（现残留 0，但新书未必） | 把 `violations` 非空的块送去 4B 复核，只处理这几条，成本可忽略 |
| 原文层不含非游戏页 | 想核对"版权页到底长什么样"时查不到 | 加 `--keep-nongame-source` 开关（默认关），只给合规/校对公司用 |
| 清单里跨行的商品名会被切坏（`狗皮大` + `衣)，$19.95` → 名字成 `衣)`） | 少量商品名不完整 | 需要"行尾续接"：上一行不以标点/数字结尾且下一行以 `)）` 开头时合并 |

这些全部写进了 `report.json` 的 `quality` 段，**每次编译自动重算**，不是一次性人工检查。

## 9.5 切完自己量一遍：自检 + 自动重切（`compiler/selfcheck.py`）

"切得对不对"不该由人来翻 2000 个块判断。切歪是有客观特征的，写成断言就能自动修：

| code | 判据 | 修法 |
|---|---|---|
| `wrapped_name` | 清单/表格行的名字括号不平衡或 ≤2 字（`衣)`） | 与同页邻块合并后重新解析名字 |
| `multi_entry` | 一块里"句首"出现 ≥2 个 `名称（NN%）` | 按条目头再切 |
| `over_long` | 超 `max_chars × 1.35` | 按句号切到上限内 |
| `fragment` | 短于 10 字且不是条目 | 并入同页相邻块 |
| `dangling_tail` | 结尾是 `，`/`；`（句子被切断） | 并入同页下一块（合并后不超长才合） |

流程：`audit → 有缺陷 → repair → 再 audit`，最多 4 轮；通过标准 = **没有硬缺陷（超长/碎片/断名）
且残留率 < 0.5%**。轮数、修复动作、修前修后指标全部写进 `report.json → selfcheck`，
所以"它凭什么说切干净了"是可复查的，不是一句"我觉得好了"。

实测（同一本书）：

```
超长块 63 → 0     碎片 19 → 0     断名（如"衣)"）→ 0
块数 2305 → 2181   平均 247 → 261 字   p95 652 → 625   最长 2165 → 702
4 轮收敛，残留 0.18%（4 条尾句为分号引导语，属正常排版）
```

块尺寸也从 900 字降到 **520 字**：一条规则不再是一整块，而是"一个判定点一块"，
DM 检索时命中的是具体那一条，而不是一整节。

## 10. 范式外推：换一本书 / 换一个系统

| 换什么 | 要改 | 不改 |
|---|---|---|
| 另一本 COC 模组（有固定剧本） | 只跑 `ingest` | 全部 |
| 另一套系统（DND/克苏鲁变体） | 词汇表 `classify.KW_*` 可能要补词；`SYNONYMS` 补别名 | 版式画像、存储、检索、时间线 |
| 一本没有书签的规则书 | 跑 `profile` 看家族打分，必要时加一个 `HeadingFamily` | 其余 |
| 小说 | 加"场景转移"识别（地点/时间标记），时间线用法不变 | 存储与检索 |
| 非中文 | 换分词器（jieba → 空格切分），`FAMILIES` 用 `latin_*` 家族 | 三层存储、开放字段 |

**判据很简单**：如果新文档需要改「存储结构」或「检索接口」，说明这套设计错了；
如果只需要加「一个标题家族」或「几个词汇」，说明它对了。

## 12. 下一步（按性价比排序）

# RPGBar 当前全局设计与进度

更新时间：2026-10-28（Asia/Shanghai）

这份文档是当前开发基线。后续实现必须先检查这里的边界，再修改具体模块。

## 目标

RPGBar 是一个剧本无关的本地 Agent DM 引擎：

```text
模型负责理解和表达
服务端负责规则、状态和事实
切分器负责提供剧本知识与可用机制
事件负责连接状态、记忆、叙事和测试
```

## 四个核心对象

### PlayDefinition

玩家选择的是玩法入口，不是孤立文件。

- `mode=sandbox`：规则库驱动，Session Zero 动态生成开局；
- `mode=scenario`：已切分的固定冒险，按场景图推进；
- `rules`：规则档案来源和公开描述；
- `knowledge`：切分器和知识库来源；
- `generation_policy`：开局生成方式；
- `content_ref`：固定内容来源，沙盒可以为空。

代码入口：`server/play_definition.py`。

### RuleProfile / RuleBinding

规则必须按 PlayDefinition 绑定：

- CoC 沙盒绑定 CoC 知识库和 d100 规则档案；
- 没有规则库的固定冒险使用明确的通用 d20 fallback；
- 不允许从全局活动剧本继承规则。

### ScriptKnowledge

切分器产生的静态知识：

- 场景、出口、检定、flag；
- NPC 和物品容器；
- `pc_card_schema`；
- `pc_relation` 静态关系图；
- 规则条目和流程图。

它不保存本局动态状态。

### FactEvent

所有真实变化必须成为服务端事实事件，再更新：

- WorldState；
- World SQLite；
- Chronicle；
- 广播；
- 测试记录。

当前 `GameState.commit_event()` 已覆盖场景、检定、flag、实体、时间、线索和关系事件；
World SQLite 与 GameState 通过补偿事务保持一致，但仍不是同一个 SQLite 原子事务边界。

## 当前运行链

```text
玩家发言
  ↓
上下文组装
  ↓
ActionJudgeAgent：只理解行动意图
  ↓
Deterministic Validator：验证当前玩法是否允许
  ↓
FactEvent Commit：提交唯一事实
  ↓
NarratorAgent：只解释已确认事实
  ↓
Risk NarrationVerifier：只审查高风险旁白
  ↓
广播 + Chronicle + 测试记录
```

## 已完成

- 本地 4B 模型和 GPU 后端；
- 动态选择剧本，不默认加载蛇王墓；
- CoC 沙盒 Session Zero；
- 固定冒险与 CoC 规则隔离；
- `pc_relation` 静态关系图接入运行时；
- World 动态关系事件；
- 角色卡 Agent 判断和服务端校验；
- ActionJudge 初版；
- 运行时已移除按固定中文动词表判断越界的旧路径；当前行动边界由
  `ActionJudge → action_validation` 根据玩法提供的场景候选和结构化状态决定；
  Narrator 只消费已确认的 blocked 结果，不再按某个剧本的词汇硬编码；
- 状态快照已加入公开 `scene_evidence`：当前场景的出口、检定、NPC、现场实体和动态关系，
  供前端、验收器和 ActionJudge 共享；其中不含 DM 内幕与检定结果文案；
- World 实体、关系和线索写工具已统一使用 `fact_transaction.commit_world_event`：
  World 写入成功前事件不会进入本轮广播，写入失败会恢复 World SQLite 快照并撤销未广播的 GameState 事件；
- CoC 沙盒 Session Zero 的圣经与开场场景初始化也会提交 `world_changed/session_zero` 事实事件，
  再广播给客户端并进入后续回放链；
- 新增 `ScriptKnowledgeAdapter`，统一把 ScriptStore/KBStore 的静态场景、目标出口、检定、
  NPC 和关系证据提供给 ActionJudge；它不读取或写入本局动态事实，动态实体/关系仍由 World 注入。
- 适配层提供只读 `timeline_template()`，可读取编译器 KB 的 `timeline_event/entity_state` 模板；
  返回值明确标记 `source=kb_template`，不会自动写入本局 World。
- NarrationVerifier；
- Chronicle 时序检索；
- 状态感知验收器；
- 统一 `PlayDefinition` 第一版。

## 尚未收口

1. `PlayDefinition` 仍需完整接管房间、Session Zero、角色卡和知识库创建流程；
2. ActionJudge 仍需在真实本地模型上继续校准置信度和歧义行为；
3. World SQLite 与 GameState 还不是同一个数据库事务；当前通过 SQLite 快照补偿回滚保持一致，
   仍需在长期并发/崩溃恢复测试中验证边界；
4. 编译器的 `entity_state/timeline_event` 是知识库侧的可选时间线模板，目前已明确不直接冒充本局状态；
   仍需补充从编译器时间线模板到 World 初始事实的通用导入协议；
5. 测试器已拿到 `scene_evidence`，还需要把它用于用例兼容性审计并区分“用例前置错误”和 DM 失败；
6. 最近一次完整 25 轮新版本验收尚未完成，不能用旧报告代替；
7. 评估 Agent 仍需要人工失败样例校准。

## 2026-10-28 真实验收记录

- 独立端口 `8010` 启动真实服务，启动日志确认没有默认加载蛇王墓，剧本由建房请求选择；
- `acceptance_stateful_smoke.json` 真实 WebSocket 执行：2/2；
- `acceptance_25.json` 真实本地模型执行两次：22/25（88%）和 21/25（84%）。
- 逐条回放后确认，当前 25 条旧用例中至少 4 条期望与状态不一致：未满足前置条件却期望移动、
  剧本没有的目标地点、没有对应检定的模糊线索、以及不在当前场景的 NPC。服务端均保持了
  `no_move/no_tool`，没有创造事实或擅自投骰；这些应进入验收器的“用例设计错误/状态不适用”类别，
  不应直接计为 DM 失败。
- 真实运行仍暴露两项待校准工作：4B 对自然语言出口目标的理解有随机性；验收集需要在每条行动上
  保存并校验 `scene / flags / present_entities / available_checks / exits` 前置快照。
- 新增 `scripts/acceptance_case_audit.py`，对验收集做剧本结构审计；当前旧 25 轮集报告 1 个错误
  （条件移动缺少前置条件）和 9 个警告（缺少起始场景、未绑定检定触发词或 NPC 范围不明），
  证明原始 25 轮分数不能直接当作 DM 质量分数。
- `player_acceptance.py` 现在按 `scene_evidence` 过滤 `present_entities / npcs / checks / exits` 前置条件，
  并在每条结果中保存 `before_evidence / final_evidence`，测试集和真实游戏共享同一状态证据。
- 验收执行器现在会显式跳过当前状态不适用的用例并记录到 `skipped_incompatible_cases`，
  不再把前置条件错误强行执行成 DM 失败。
- 新增 `scripts/build_stateful_acceptance.py`：直接从切分器场景/出口/检定生成带前置证据的
  验收集骨架，模型只可扩写自然语言，不能决定或删除服务端前置条件。
- 结构化 25 条用例已通过审计（0 errors / 0 warnings）；真实本地模型执行 13 条当前可达用例，
  13/13 通过，另外 12 条因前置 flag/场景尚未达到而被明确记录为 skipped，未计入 DM 失败。
- `scripts/session_zero_live_check.py` 通过真实 WebSocket 验证 CoC 沙盒开局会收到
  `world_changed/session_zero` 事实事件；启动日志同时确认使用 CoC d100 规则与动态沙盒玩法。
- 知识适配层接入后，真实 `acceptance_stateful_smoke.json` 仍为 2/2；服务端日志确认房间正常创建、
  ActionJudge/Narrator 工具链正常结束，未出现服务生命周期崩溃。

## 开发顺序

1. 统一 PlayDefinition 与规则、知识库、角色卡、Session Zero 的绑定；
2. 统一 ScriptKnowledge 运行时适配器；
3. 收拢 ActionJudge 和 Deterministic Validator，逐步移除旧的重复裁定路径；
4. 让所有 World 写操作通过 FactEvent 事务提交；
5. 更新状态感知测试集和语义评估；
6. 用同一套 25 轮和跨玩法实验验收；
7. 只有测试结果证明架构改动有效后，才继续调整模型提示词。

## 约束

- 不使用 LangChain 或 LangGraph；
- 不按某个剧本写服务端分支；
- 不把关键词表当通用规则；
- Agent 不得直接改事实；
- 旁白不得成为事实来源；
- 角色卡是否需要由 Agent 根据玩法和规则证据判断；
- 规则、状态、事实和记忆必须可回放、可测试、可追溯。

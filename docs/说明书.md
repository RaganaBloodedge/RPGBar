# RPGBar 使用说明书

> 版本：v0.6（真实模组示例 + 剧本可切换）　更新时间：2026-10-09
>
> 各版本变更见 [CHANGELOG.md](../CHANGELOG.md)；服务器启动横幅、`GET /api/version` 与网页顶栏都会显示当前版本号。

---

## 一、项目概述

RPGBar 是一款**多人联机文字跑团（TRPG）**游戏：一个 AI Agent 担任地下城主（DM），用 RAG 技术约束 DM 严格遵循剧本推进剧情；多名玩家通过浏览器连接服务器实时联机，各自可以召唤「小助手」草拟行动，骰子由服务端统一投掷。

**核心特点**

| 特点 | 说明 |
| --- | --- |
| Agent 当 DM | DM 负责叙事、裁定检定、推进剧情 |
| RAG 守剧本 | 检索剧本相关片段注入 DM，约束它不跑偏 |
| 剧情状态机 | 章节→场景→节拍，flag / 出口 / 检定门控 |
| 多人联机 | WebSocket 房间，多玩家实时同步 |
| 服务端权威骰子 | 玩家只发意图，结果由主机投掷（防作弊） |
| 云/本地双路径 | DM 可走云 API，也可走玩家本地 llama.cpp |
| 可中途加入 | 对局进行中也能加入，DM 自动补剧情 |

**当前形态**：Web 联机 demo。服务器是独立进程，跑在某个玩家（主机）的电脑上，其他玩家连进来一起玩。后续移植 Unity。

## 二、已实现功能清单

1. **多人联机房间**：按房间码隔离，玩家加入/离开实时广播，状态全量同步。
2. **三个标准 Agent（一个任务引擎，多条固定 COT）**：模型自己决定调哪个工具 → 服务端执行 → 结果回灌 → 循环到收尾；
   固定流程的任务（生成人物小传、算反应权重）走单轮 JSON。
   - 主机 DM（大模型）：只读工具 + 写工具（移动/加线索/投骰/补 NPC 人设）。
   - 主机小助手（小模型）：`persona` / `react_weights` 等固定流程，负责 NPC 人设与后续摘要。
   - 玩家小助手（小模型）：**只有只读工具**，结构上改不了剧情。
3. **提示词分层**：各 Agent 的 **System prompt 只写各自职责**；剧本的世界观、语气、切片索引由
   `script_loader` 自动切片后生成**次级 prompt**，排在 System prompt 之后作为第二条 system 消息。换剧本不动人格。
4. **剧本读取接口 + 自动切片**：读剧本文件（结构化 JSON 或无结构 `.md`/`.txt`）→ 自动切片 →
   生成次级 prompt，并顺带自检（出口断链、不可达场景、`start_scene` 缺失、缺 `system` 段）。
5. **RAG 剧本检索**：jieba 分词 + BM25，检索与当前行动最相关的场景片段。
6. **剧情状态机**：场景推进、flag 门控、出口条件、检定触发。
7. **服务端权威骰子**：d20 检定 + 自由掷骰，支持设种子复现。
8. **两条模型通道 + 游戏内接入**：云 API 与本地模型（llama.cpp / Ollama / LM Studio）走同一套 OpenAI 兼容协议；
   顶栏「⚙ 设置」可现场接入，含**测试连接**与工具调用能力探测；Key 只存玩家本机浏览器。
9. **护栏做在工具里**：`move_to` 只接受当前场景已解锁的出口、`set_flag` 只接受剧本声明过的 flag、
   骰子只能由服务端投——不是靠在提示词里恳求模型别乱来。
10. **脚本化兜底**：三个槽位默认留空，DM 走 `dm.py` 的确定性流水线、NPC 走内置原型兜底，玩法完整可玩；接一个就启用一个 Agent。
11. **模型不支持工具调用时的降级**：自动切到单轮 JSON 协议，功能不减。
12. **剧本库 + 可切换**：《古堡秘宝》（原创，5 场景）与《蛇王墓 · 第一层「假墓」》（改编自真实模组，9 场景 / 12 线索 / 11 处检定）；
    可用 `config.json` 的 `script`、环境变量 `RPGBAR_SCRIPT`、或**游戏内「⚙ 设置 → 剧本」卡片**（含 HTTP 接口）切换；剧本名会显示在界面与 `/api/version` 上。
13. **中途加入 + DM 补剧情**：任何时刻凭房间码加入既有对局；DM 自动生成带入旁白（老玩家同步可见），并给新玩家一份私有的「故事回顾」。
14. **NPC 自动人设 + 反应权重**：剧本外的次要 NPC 首次被互动时由主机小助手现场生成人物小传；
    有后果的互动再算一次反应权重，**落点由服务端骰子决定**（模型只给区间）。侧栏「在场人物」实时同步已遇到的 NPC（含外号）。
    NPC 的交往记录与好感度留在 `NpcMemory`，**不进 DM 的剧情记忆**。
15. **一键启动**：`start.bat`（Windows）/ `start.sh`（Linux/macOS）。
16. **自动化测试**：236 项 Python 冒烟测试（进程内确定性 + 实时联机 + 中途加入 + 模型设置 + 剧本接口 + NPC 子系统），
    外加可选的 71 项前端 DOM 校验（`scripts/ui_check.js`，需 Node + jsdom）。

## 三、系统架构

```
┌─────────────────────────┐         ┌──────────────────────────────┐
│      玩家客户端（网页）    │         │     服务器（主机玩家电脑）       │
│                         │  WebSocket │                              │
│  旁白流 / 掷骰 / 输入     │ ◄────────► │  FastAPI + WebSocket 房间      │
│  ⚙ 设置（模型 + 剧本）    │   join     │  ├─ NarratorAgent（主机 DM）   │
│  在场人物 / 线索         │  configure │  │   └─ 工具循环 + 护栏         │
│  AdvisorAgent 小助手 ◄───┼── action ──┤  ├─ AssistantAgent（主机小助手）│
│  （未来：本地 3B/4B 模型）│  suggest  │  │   └─ persona/react_weights  │
│                         │  roll     │  ├─ AdvisorAgent（玩家小助手）  │
│                         │           │  ├─ NPC 子系统（人物卡/别名/记忆）│
│                         │           │  ├─ 剧本读取/切片（script_loader）│
│                         │           │  ├─ RAG 检索（jieba+BM25）     │
└─────────────────────────┘           │  ├─ 剧情状态机（场景/flag/出口）  │
        ▲ HTTP: /api/scripts/*         │  ├─ 服务端骰子                 │
        └──────────────────────────────┤  └─ LLM Provider（云/本地同套） │
                                       └──────────────────────────────┘
```

- **服务器**（`server/`）：独立进程，承载所有权威逻辑。玩家**不自己起服务**，只连服务器。
- **客户端**（`web/`）：纯静态网页，通过同源 WebSocket 连接服务器。
- **三个模型槽位**：`dm`（大模型，房主配置，全房共用）、`assistant`（小模型，房主配置，
  负责 NPC 人设/反应权重/摘要）与 `advisor`（小模型，每人各配各的）。
  槽位可在配置里预置，也可在游戏内「⚙ 设置」里运行期改——**留空则退回确定性流水线，玩法不变**。
- **提示词两层**：System prompt 只定义 Agent 职责；剧本内容（世界观/语气/切片索引）由
  `server/script_loader.py` 读取剧本自动切片后生成**次级 prompt**，作为第二条 system 消息。
- **中途加入**：房间在新玩家加入前若已开局，服务器广播 DM 的带入旁白（全员可见），并向该玩家单独推送 `recap`（私有回顾，不打扰其他人）。

### 目录结构

| 路径 | 说明 |
| --- | --- |
| `server/main.py` | FastAPI + WebSocket 房间服务（入口），三个模型槽位运行期配置 + 剧本读取/切换接口 + NPC 同步 |
| `server/script_loader.py` | 剧本读取 → 自动切片 → 生成次级 prompt；含剧本结构自检 |
| `server/agents/base.py` | Agent 骨架：两层提示词 + 工具注册 + 工具调用循环 + 两条降级路径 |
| `server/agents/tool_agent.py` | 小模型任务引擎：一条任务 = 一条固定 COT，单轮 JSON / 带工具两条路 |
| `server/agents/narrator.py` | 主机 DM Agent（大模型，持有写工具） |
| `server/agents/persona.py` | 主机小助手 Agent（小模型，`persona` / `react_weights` 任务） |
| `server/agents/advisor.py` | 玩家小助手 Agent（小模型，只有只读工具） |
| `server/npc.py` | NPC 子系统：人物卡 / 别名索引 / 原型兜底表 / NPC 私有记忆（好感度） |
| `server/dm.py` | 无模型时的确定性剧本编排（留空 API 的兜底） |
| `server/rag.py` | 已切片剧本的持有者 + jieba/BM25 检索 |
| `server/state_machine.py` | 场景/flag/出口/检定的权威状态 |
| `server/dice.py` | 服务端骰子（可复现，含加权采样 `weighted_pick`） |
| `server/llm.py` | OpenAI 兼容 Provider（云/本地同套），含工具调用与降级判定 |
| `server/config.py` | 配置加载（`models.dm` / `models.assistant` / `models.advisor` 三个槽位） |
| `web/` | 玩家客户端（HTML/CSS/JS），含设置抽屉（模型 + 剧本）与在场人物面板 |
| `scripts/sample_script.json` | 剧本《古堡秘宝》（原创，默认） |
| `scripts/totsk_l1.json` | 剧本《蛇王墓 · 第一层「假墓」》（改编自 Tomb of the Serpent Kings） |
| `scripts/smoke_test.py` | 冒烟测试（236 项） |
| `scripts/ui_check.js` | 可选：前端 DOM 校验（71 项，需 Node + jsdom） |
| `start.bat` / `start.sh` | 一键启动脚本 |

## 四、快速开始

### 4.1 环境要求

- Python 3.10+
- 能访问同一网络（局域网）或多台能互通的机器

### 4.2 启动服务器（主机玩家）

```bash
pip install -r requirements.txt
python -m server.main
```

或 Windows 直接双击 `start.bat`。启动后终端会打印：

```
[RPGBar] 服务器监听 0.0.0.0:8000
[RPGBar] 本机访问: http://127.0.0.1:8000
[RPGBar] 局域网访问（发给朋友）: http://192.168.x.x:8000
```

### 4.3 玩家加入

把「局域网访问」地址发给朋友，对方浏览器打开即可：

1. 输入名字 + 选择职业（战士/法师/游侠/盗贼）
2. 房间码留空自动建房，或输入朋友的房间码加入
3. 进入游戏，开始跑团

> **跨网络**：不同网络的朋友要连你，需要给服务器电脑做公网映射 / 内网穿透（frp、cpolar 等），或把服务器部署到云主机。

## 五、玩法指南

### 5.1 界面

- **左侧**：旁白/对话流（DM 旁白金色、玩家行动蓝色、骰子结果绿色/红色、系统提示居中）
- **右侧**：队伍成员、已获得的线索（flag）、自由掷骰
- **底部**：行动输入框 + 「助手建议」按钮 + 发送
- **顶栏**：「复制房间码」、**「⚙ 模型」**（接入大模型/本地模型），以及一个模型状态胶囊

### 5.2 行动

在输入框描述你的行动，回车发送。例如：

- `说服老周` —— 触发「魅力」检定
- `调查挂毯` —— 触发「调查」检定
- `推开铁门进入门厅` —— 移动场景
- `我四处张望` —— 自由发挥，由 DM 即兴旁白

### 5.3 骰子与检定

- 检定：当你做出对应行动（如说服、调查、战斗）时，DM 自动投 d20，与难度 DC 比较，成功/失败各有剧本写好的结果，并广播给所有人。
- 自由掷骰：点右侧「掷 d20」按钮，纯娱乐。
- 骰子在**服务端**投掷，玩家无法作弊。即使 DM 接了模型，模型也只能「请求投骰」，拿不到骰子，也就编不出结果。

### 5.4 小助手建议

点「助手建议」，会基于当前场景给出 2-4 条可执行建议，点击即发送。

- 建议下方会标注来源：`脚本化兜底`（没接模型）或 `小模型 · 用了 xxx`（接了模型，附带它实际调用的工具名）。
- 小助手是**只读**的：它的工具集里没有任何能改游戏状态的东西，所以它给建议，但绝不会替你改剧情。

### 5.5 模型设置（⚙ 设置 → 模型）

点顶栏「⚙ 设置」打开抽屉，「模型」部分三个槽位分别配置：

| 槽位 | 谁能改 | 说明 |
| --- | --- | --- |
| **主机 DM · 大模型** | 仅房主 | 推进剧情、投骰判定、扮 NPC，全房间共用 |
| **主机小助手 · 小模型** | 仅房主 | 生成 NPC 人物小传、算反应权重、后续做剧情摘要；默认指向 `127.0.0.1:8081` |
| **玩家小助手 · 小模型** | 每个玩家自己 | 只读场景给建议，可以指向你自己电脑上的本地模型 |

> 两台小助手其实是**同一个任务引擎**（`server/agents/tool_agent.py`）上的不同任务——生成建议、生成人物小传、
> 算反应权重各自是一条独立流程，本质上是同一个工具 Agent 的不同「岗位」。

每个槽位三选一：**关闭** / **云 API** / **本地模型**。

- 有常用预设（DeepSeek、OpenAI、智谱 GLM / llama.cpp、Ollama、LM Studio），点一下即填好地址与模型名。
- **「测试连接」**：真的发一次请求；如果通，还会额外探测该模型**是否支持工具调用**，
  并告诉你它是走「标准 Agent 工具循环」还是「单轮 JSON 降级协议」。
- **「保存并连接」**：立即生效（服务端重建 Agent），同时存进你浏览器的 localStorage，下次进房自动应用。
- **「清除本机设置」**：清掉本机保存的配置，并让服务端把三个 Agent 退回脚本化。

两条安全约定：

1. **API Key 只留在你自己的浏览器里**，服务端只在内存中使用，任何下发给客户端的消息都不含明文 key。
2. 非房主改主机 DM / 主机小助手会被拒绝并收到提示（界面上这两张卡片直接是锁定状态）。

### 5.5.1 NPC 自动人设与反应判定

剧本里点名的主角 NPC 自带人设；但玩家临时搭话、动手的路人，剧本里没有写——
以前他们就是「没有灵魂的空壳」。现在由**主机小助手**现场补齐：

- **人物小传（`persona` 任务）**：结合剧本世界观，为这个 NPC 生成身份、性格、语气、目标、忌讳，
  存成一张**人物卡**（`server/npc.py` 的 `PersonaCard`）；之后 DM 的扮演都以这张卡为准。
- **反应权重（`react_weights` 任务）**：当玩家做出**有后果**的互动（殴打 / 恐吓 / 救助 / 施舍……）时，
  小助手给出若干反应选项及其**权重区间**（如「息事宁人 0.7 / 报警 0.1 / 还手 0.2」）。
  服务端再用 `dice.weighted_pick` 采样定落点——**模型看不到骰点，也编不出结果**。
- **记忆隔离**：NPC 的交往记录与好感度留在 `NpcMemory` 里；DM 只收到「人物卡 + 当前状态快照」这样的
  提炼结论，**不会**被 NPC 的流水账占用剧情上下文。
- **原型兜底**：不接模型时，NPC 按内置的六类原型（平民 / 暴徒 / 商人 / 卫兵 / 学者 / 权贵）建档与反应，
  行为稳定、玩法完整。
- **别名（外号）**：玩家给 NPC 起的外号会被记进别名索引，`resolve` / `detect` 支持按名字或外号认出同一个 NPC
  （BM25 检索命中外号时也能对上人）。

侧栏「在场人物」面板实时同步当前房间已遇到的 NPC（名字 · 身份），鼠标悬停可看别称。

### 5.6 剧本读取与切换（⚙ 设置 → 剧本）

同一个抽屉的上半部分是**剧本**卡片：

- **可用剧本列表**：列出 `scripts/` 目录下的 `.json` / `.md` / `.txt`，每项显示标题、格式、场景数与切片数；
  当前正在用的那个标「当前」。
- **读取并切片**：填入文件名（或点列表项）后点它，服务端会读取文件 → 自动切片 → 返回切片清单，
  并生成两份**次级 prompt**（DM 用的完整版、小助手用的公开版），可以在下方折叠区直接看。
- **设为活动剧本**：**仅房主可用**。切换后新开的房间使用新剧本；**已经在玩的房间不受影响**
  （房间在创建时就固定了自己的剧本副本）。
- **粘贴剧本内容**：不想放文件也行——粘贴 Markdown 或 JSON，服务端自动识别格式并切片。

> 出于安全考虑，服务端只允许读取 `scripts/` 目录内的文件（服务器默认绑 `0.0.0.0`，不能变成任意文件读取接口）。
> 想用别处的剧本，把它拷进 `scripts/`，或直接粘贴内容。

切片与自检的细节见 §6.4。

### 5.7 线索（flag）与分支

成功完成某些检定会获得线索（如 `found_secret_door` 发现暗门），右侧「已获得线索」会列出。这些 flag 用于解锁后续出口，形成分支剧情。

侧栏显示的是 flag 的中文描述（在剧本的 `flags` 段里定义），新玩家看回顾时也是这些描述，比 `has_key` 这样的内部名友好得多。

### 5.8 中途加入

**任何时刻都能加入**——对局进行到一半，朋友打开链接、填上房间码即可，不需要重启房间或等人齐。

加入时会发生两件事：

1. **全员可见的带入旁白**：DM 会写一段话，让新角色自然地登场，并顺带复述此前的关键进展。老玩家也能看到，所以剧情上是连贯的（"一个人推门进来了"），不会突兀。
2. **新玩家私有的「故事回顾」面板**：一张卡片，分三行给出
   - **行程**：走过的场景链（如 `古堡大门 → 门厅`）
   - **线索**：队伍已获得的 flag 中文描述
   - **最近动态**：最近若干条玩家行动记录

三种情况都不会触发补课（按正常加入处理）：房间刚建、只有一个人且什么都没做、或者房间已经空了重开一局。

> 补课内容由 DM 生成：配了 LLM 就由模型写（受「不剧透内幕、不编造剧本外内容」约束），没配就由服务端拼接行程 + 线索 + 当前场景原文——两种情况下信息量都不缺。

## 六、DM 与剧本

### 6.1 DM 如何守剧本

DM 有**两条路径**，取决于主机 DM 槽位是否接了模型，但两者**共用同一套状态机与骰子**，玩法与规则完全一致。

两条路径的提示词都是**两层**的：System prompt 只写职责（"你是主持人，命中检定就投骰、命中出口就推进场景……"），
剧本的世界观、语气与切片索引由**次级 prompt** 承载，作为第二条 system 消息紧跟其后。这样换剧本只换第二层。

**A. 接了模型 → NarratorAgent 工具调用循环**

模型每一轮可以做一件事：调工具。它能用的工具分成两类：

| 类型 | 工具 | 说明 |
| --- | --- | --- |
| 只读 | `read_scene` `list_exits` `list_checks` `lookup_script` | 看场景原文（含 DM 内幕）、看出口与条件、看可触发的检定、按关键词检索剧本 |
| 写（改状态） | `move_to` `set_flag` `roll_check` | 推进场景、记录线索、请求服务端投骰 |

护栏**做在工具体里**，模型绕不过去：

- `move_to` 只接受「当前场景列出的、且条件已满足的出口」；给个不存在的场景会返回错误，让模型重试。
- `set_flag` 只接受剧本声明过的 flag（白名单从剧本自动收集）。
- `roll_check` 是唯一的骰子来源——**模型拿不到骰子，也就编不出结果**；投完由服务端广播权威结果，模型只补一句衔接。
- 最后用 `finish` 收尾。

**B. 没接模型 → `dm.py` 确定性流水线**

1. **匹配检定**：命中某个检定 → 服务端投骰 → 应用剧本写好的成功/失败结果。
2. **匹配出口**：命中某个出口 → 校验 flag 条件，满足则推进场景，不满足则提示「还做不到」。
3. **自由发挥**：用剧本原文 + 提示引导拼出旁白。

匹配采用「命中关键词数 + 最长命中长度」打分，检定与出口**同台比较**（同分优先检定，因为检定不改场景、误判代价更小），避免「进入/进去」这类泛化词误配。

### 6.2 剧本格式

剧本是结构化 JSON（`scripts/sample_script.json`），结构如下：

```json
{
  "title": "古堡秘宝",
  "premise": "一句话公开背景（给小助手的次级 prompt 用，可选）",
  "system": "剧本的世界观与语气（进次级 prompt，不再拼进 System prompt）",
  "start_scene": "gate",
  "flags": {
    "knows_backdoor_key": "从老周口中打听到后门钥匙藏在内院枯井旁",
    "has_key": "取得了开启密室后门的钥匙"
  },
  "scenes": [
    {
      "id": "gate",
      "chapter": 1,
      "title": "古堡大门",
      "location": "古堡正门外",
      "public_text": "给玩家看的旁白",
      "dm_notes": "只有 DM 知道的内幕",
      "npcs": [{"name": "老周", "role": "看守", "style": "胆小", "knows": "后门钥匙在井旁"}],
      "keywords": ["大门", "铁门", "古堡"],
      "flags_required": [],
      "flags_set": [],
      "checks": [
        {
          "id": "persuade_zhou",
          "skill": "魅力",
          "dc": 12,
          "keywords": ["说服", "套话", "老周"],
          "success": "成功时的旁白",
          "fail": "失败时的旁白",
          "success_flag": "knows_backdoor_key"
        }
      ],
      "exits": [
        {"to": "hall", "label": "推开铁门进入门厅", "keywords": ["铁门", "门厅"], "condition": null}
      ]
    }
  ]
}
```

**字段说明**

| 字段 | 说明 |
| --- | --- |
| `title` / `system` / `start_scene` | 剧本名 / 世界观与语气（进次级 prompt）/ 起始场景 id |
| `premise` | 可选。一句话**公开**背景，会给小助手的次级 prompt（不含内幕） |
| `flags` | flag 的中文描述表：`{flag 名: 一句人话}`，用于侧栏线索与新人回顾 |
| `scenes[].id` | 场景唯一标识 |
| `public_text` | 玩家可见旁白（进入场景时广播） |
| `dm_notes` | 仅 DM 可见的内幕/暗线（RAG 注入，但不直接播给玩家） |
| `npcs[]` | NPC 卡：名字/身份/说话风格/知道什么 |
| `keywords[]` | 检索与匹配用的关键词 |
| `flags_required` | 进入该场景需满足的 flag |
| `flags_set` | 进入场景时自动设置的 flag |
| `checks[]` | 检定：技能、难度 DC、触发关键词、成功/失败文案、成功奖励的 flag |
| `exits[].condition` | 出口可用条件：`null` 恒可用，或填 flag 名（拥有该 flag 才可用） |

### 6.3 如何写新剧本

1. 复制 `scripts/sample_script.json`，改名。
2. 改 `title`、`system`、`start_scene`，编写各 `scenes`。
3. 在 `flags` 段里给每个 flag 写一句中文描述（不写也能跑，只是侧栏和回顾会显示 flag 内部名）。
4. 指向新文件即可，**不用改代码**——三选一：

```bash
# ① 环境变量
RPGBAR_SCRIPT=scripts/我的剧本.json python -m server.main

# ② config.json 里的 script 字段
{ "script": "scripts/我的剧本.json" }

# ③ 游戏内「⚙ 设置 → 剧本」读取并切换（房主，无需重启服务器）
```

> 把文件放进 `scripts/` 目录是必须的：剧本接口出于安全只允许读该目录。
> 也可以完全不放文件——在设置里直接粘贴剧本内容，服务端会自动识别 JSON / Markdown。

> 写剧本时有一条容易踩的规则：**检定优先于出口**（同分时）。所以「用来说出口的那句话」不要出现在任何检定的关键词里，否则玩家想走却被判成检定。真实例子：《蛇王墓》里「侧身钻进棺后的窄缝」原会被「检查北墙」检定的关键词抢走——把检定的关键词收窄后就好了。引擎在 0.6.0 起改为**按匹配打分比较**检定与出口，但关键词不重叠仍然是最稳的写法。

> flag 白名单**不需要手动维护**：服务端会从剧本里（`flags` 段 + 各场景的 `flags_set` / `flags_required` / `checks[].success_flag`）自动收集合法 flag，LLM 只能设置这些。

### 6.4 切片与次级 prompt

读取剧本的入口是 `server/script_loader.py`（`parse_script` / `read_script_file`），一次做三件事：

**① 读取**：支持结构化 JSON，也支持无结构文本（`.md` / `.txt`）。

**② 自动切片**：

| 输入 | 切法 |
| --- | --- |
| 结构化 JSON | 每个场景一片（`kind=scene`，id 与场景 id 相同），另加一片「剧本设定」（`kind=meta`，内容 = `system` 字段） |
| 无结构文本 | 按 Markdown 标题（`#`/`##`/…）切段；单段超过 900 字就按段落装箱成多片。切片 id 形如 `c01`、`c02` |

无结构文本无法表达出口与检定，因此引擎会**按切片顺序合成一条线性场景链**（每片指向下一片），
让纯文本剧本也能直接开局试玩——界面上会明确提示这是降级模式。

**③ 生成次级 prompt**（`build_script_prompt`），有两个版本：

| 版本 | 给谁 | 内容 |
| --- | --- | --- |
| 完整版 | 主机 DM | 剧本名 + 来源 + 世界观/语气原文 + **切片索引**（id / 标题 / 字数 / 关键词） |
| 公开版 | 玩家小助手 | 剧本名 + `premise` 背景 + "只能建议剧本中真实存在的行动"的约束 |

公开版刻意**不含切片索引与 DM 内幕**——小助手只需要知道"别发明东西"，不需要知道剧本全貌（最小权限 + 防剧透）。

索引里**只列标题不展开正文**（正文交给 `read_scene` / `lookup_script` 按需读取），所以次级 prompt 的体量不随剧本长度线性膨胀——剧本再长，放进提示词的也只是几行索引。

**④ 顺带自检**：读取时报告出口断链、无法从开局到达的场景、`start_scene` 不存在、缺 `system` 段等问题。
这些会显示在启动横幅、`GET /api/scripts` 与游戏内剧本卡片上。
（这一条抓出过真实问题：默认剧本《古堡秘宝》的「守护者之战」原先没有任何入口，已补上密室 → 决战的出口。）

## 七、接入大模型

三个 Agent 都使用 **OpenAI 兼容接口**，所以**云 API 与本地模型（llama.cpp / Ollama / LM Studio）是同一套 Provider，只是 `base_url` 不同**。

有两条接入途径，任选其一（也可以都不用）。

### 7.1 游戏内接入（推荐）

顶栏「⚙ 设置」→「模型」部分 → 选通道 → 填地址与模型 → 「测试连接」→「保存并连接」。详见 §5.5。
配置存在浏览器本机，Key 不会离开你的机器。

### 7.2 配置文件 / 环境变量接入

```bash
# 主机 DM（大模型）—— 云 API
export RPGBAR_DM_MODEL_API_KEY="sk-xxx"
export RPGBAR_DM_MODEL_BASE_URL="https://api.deepseek.com/v1"
export RPGBAR_DM_MODEL_MODEL="deepseek-chat"

# 主机小助手（NPC 人设 / 反应权重 / 摘要）—— 本机小模型，不需要 key
export RPGBAR_ASSISTANT_MODEL_KIND="local"
export RPGBAR_ASSISTANT_MODEL_BASE_URL="http://127.0.0.1:8081/v1"
export RPGBAR_ASSISTANT_MODEL_MODEL="qwen2.5-3b-instruct"

# 玩家小助手（小模型）—— 本机 llama.cpp，不需要 key
export RPGBAR_ADVISOR_MODEL_KIND="local"
export RPGBAR_ADVISOR_MODEL_BASE_URL="http://127.0.0.1:8080/v1"
export RPGBAR_ADVISOR_MODEL_MODEL="qwen3-4b"
```

或复制 `config.example.json` 为 `config.json`，填 `models.dm` / `models.assistant` / `models.advisor` 三段。

> 旧变量 `RPGBAR_LLM_API_KEY` / `_BASE_URL` / `_MODEL` 仍可用，会自动映射到主机 DM 槽位。

```bash
# 本地模型怎么起：llama.cpp 的 llama-server 暴露 OpenAI 兼容端点
llama-server -m qwen3-8b.Q4_K_M.gguf --port 8080
```

DeepSeek / 智谱 GLM / 通义 Qwen 均兼容云 API，改 `base_url` + `model` 即可。

### 7.3 三条降级路径（保证「没接模型也能玩」）

| 情况 | 行为 |
| --- | --- |
| 槽位 `kind=off`（默认） | 该 Agent 走脚本化兜底：DM 走 `dm.py` 流水线，小助手直接给剧本里的出口与检定关键词 |
| 云 API 没填 key | 同上（配置不完整时按未接入处理，不会报错卡住） |
| 模型不支持工具调用 | 自动切到**单轮 JSON 协议**：`{"narration": "...", "move_to": "...", "set_flags": [...]}`，功能不减，只是少了多轮工具往复 |
| 调用过程中出错 | 已成功的工具效果保留，旁白补一段脚本化兜底（不会让一局卡死） |

「测试连接」会把第 3 种情况直接告诉你。

## 八、技术实现细节

### 8.1 RAG 检索

- 分词：`jieba`
- 打分：`rank-bm25`（BM25Okapi）
- 每个场景的可检索文本 = 标题 + 地点 + 关键词 + NPC 名 + 公开文本
- 检索结果：当前场景永远排第一，其余按 BM25 分数取 top-k，注入 DM 上下文

### 8.2 剧情状态机

- `GameState` 持有：玩家、flag 集合、当前场景、历史、回合数
- 出口条件：`condition` 为空恒可用，否则要求对应 flag 在集合中
- 服务端权威：客户端只收到状态快照（`state` 消息），不直接改状态

### 8.3 服务端权威骰子

- `dice.roll_check(skill, dc)`：d20 检定，返回 `{skill, dc, roll, success}`
- 支持 `dice.seed(n)` 设种子，便于测试复现

### 8.4 行动匹配：打分制，检定与出口同台比较

玩家输入先切词，对「检定」与「出口」各自的候选算一个分数：`(命中关键词数, 最长命中关键词长度)`。

- 取各自的最高分，**两者比大小**，谁更贴合玩家的措辞就走谁；同分优先检定（检定不改场景，误判代价更小）。
- 这样既避免了泛化词误配（如「进入／进去」把「打开暗门进入密室」抢到别的门上），也避免了「检定无条件抢占出口」。
- 出口命中但条件不满足时，DM 回一句「你想…但眼下还做不到」，把门控如实告诉玩家。

### 8.5 护栏：做在工具里，而不是「事后校验 JSON」

接了模型时（`server/agents/`），Agent 骨架跑一个标准工具循环：

```
组装 messages（System 职责 + 次级 prompt（剧本）+ 本轮上下文）
┌─→ 调模型（带上工具的 JSON Schema）
│    ├─ 模型返回 tool_calls → 服务端逐个执行 → 结果以 role="tool" 回灌 ─┐
│    └─ 模型给出终稿 / 调 finish → 结束                                 │
└──────────────────────────────────────────────────────────────────────┘
步数用尽 → 明确要求模型收敛为最终结果（不再给工具）
```

护栏不在提示词里，而在**工具体内部**：

- `move_to`：只能是当前场景 `exits` 里列出的、且 `condition` 已满足的出口；否则返回 `{"error": ..., "available": [...]}` 让模型重试。
- `set_flag`：只能设置剧本自动收集的 flag 全集里的名字，否则返回 `{"error": ..., "allowed": [...]}`。
- `roll_check`：**骰子只在这里产生**，且由 `dice.roll_check` 在服务端投；模型既拿不到骰子，也没法编造结果。
- `npc_introduce`：让 DM 请求为某个现场 NPC 补齐人设；实际建档走主机小助手，DM 拿回的是人物卡，不是自己编的设定。
- 写工具只存在于 NarratorAgent。AdvisorAgent 的工具集里**根本没有**写工具，「小助手不会改剧情」是结构性的。

**校验器同样是护栏**：走单轮 JSON 的任务（`persona` / `react_weights`）在 `validate` 里做字段裁剪、
范围 clamp、权重归一化、选项封顶——模型输出再离谱，落到系统里的一定是合法值。
NPC 反应的落点由 `dice.weighted_pick` 采样，**模型只提供权重区间**。

每次工具调用都会记进 `AgentResult.steps`（工具名 + 参数 + 结果），用于界面展示与测试断言。

### 8.6 任务引擎：一个引擎，多条固定 COT

两台小助手共用 `server/agents/tool_agent.py` 的 `ToolAgent`。每个任务是一个 `Task`：
`system`（职责）+ `secondary`（如剧本世界观）+ `user`（本轮上下文）+ `json_hint`（输出 schema）
+ `validate`（校验兜底）+ `fallback`（无模型时的确定性实现）。

- **带工具的任务**（`action_advice`）走标准工具循环；
- **无工具的任务**（`persona` / `react_weights`，未来的 `summarize`）走单轮 JSON。

两条路都保留「无 provider → `fallback`」「不支持 tools → 单轮 JSON」「出错 → 降级」三条兜底，
所以**任何一条任务都没有模型也能跑通**。

## 九、测试

```bash
python scripts/smoke_test.py            # 进程内 + 实时联机（需先起服务器）
python scripts/smoke_test.py --unit     # 仅进程内

npm i jsdom && node scripts/ui_check.js # 可选：前端 DOM 校验（需服务器在跑）
```

**Python 侧 236 项**，覆盖：

- 基础：剧本加载、版本号与 CHANGELOG 一致性、RAG 检索命中、flag 门控、剧本驱动 flag 白名单、骰子复现、检定/出口/建议、剧情回顾与 DM 引导兜底。
- 蛇王墓专项：结构自检（出口无断链、门控 flag 在册、可达性、原作署名与许可仍在）、线索中文描述、**检定/出口优先级回归**（「侧身钻进棺后的窄缝」必须判为出口而非检定）、一局**完整通关**（开场 → 七间墓室 → 石门 → 假王之墓 → 秘道，集齐全部 12 条线索）。
- **剧本读取与切片层**：结构化剧本切片数/id 对应关系、设定切片含 `system` 原文、无结构文本按标题切段与超长装箱、纯文本自动合成线性场景链、剧本自检（`start_scene` 缺失 / 出口断链 / 不可达场景 / 缺 `system` 段）与缺省字段补齐。
- **提示词分层**：System prompt 只含职责（不含剧本标题、场景 id、剧本正文）、次级 prompt 含世界观与切片索引、
  小助手的次级 prompt 为公开版（无索引、无内幕）、消息三层结构为 `system → system → user`、
  **实际发给模型的请求里确实带了第二条 system 消息**；DM 的确定性流水线同样两层。
- **Agent 层（不需要真实模型）**：用一个按脚本吐回复的假 Provider 验工具循环——`move_to` 真的改了状态、非法出口被拒且状态不变、未声明的 flag 记不进去、`roll_check` 产出真实骰子事件、trace 顺序正确、工具结果以 `role="tool"` 回灌。
- **任务引擎层**：无模型走 `fallback`、单轮 JSON 解析、非法输出被 `validate` 裁剪、只发一次 chat、不合规回落 degraded、未知任务名报错。
- **NPC 子系统**：剧本播种、原型兜底建档、模型建档字段 clamp、别名（外号）归并、
  反应权重与**固定种子可复现**、模型输出里不含骰点字段、`weighted_pick` 边界、记忆隔离（好感度可见、流水账不外泄）、
  DM 工具集有无 `npc_card`/`npc_introduce`、选项封顶与空选项兜底。
- **权限边界**：小助手工具全为只读、结构上不含写工具、读场景不下发 DM 内幕。
- **降级路径**：无 provider 走确定性流水线；模型不支持工具调用时切单轮 JSON 且仍生效。
- **槽位与安全**：Provider 槽位矩阵（off / 缺 key / 齐活 / 本地免 key）、槽位字段清洗（非法 kind 丢弃、非 http 地址丢弃、temperature 夹取值域、未提交的 key 保持原值）、对外状态**绝不含明文 key**。

## 十、打包发布（发给朋友）

### 10.1 打包成 exe

```bash
pip install pyinstaller
pyinstaller --name RPGBarServer --onedir --noconfirm --clean \
  --add-data "web;web" \
  --add-data "scripts;scripts" \
  --add-data "config.example.json;." \
  --collect-all jieba \
  --exclude-module uvloop --exclude-module watchfiles \
  run_server.py
```

产物在 `dist/RPGBarServer/`，把给玩家的说明拷进去再压缩即可发送：

```bash
cp docs/使用指南.txt dist/RPGBarServer/使用指南.txt
python -c "import shutil; shutil.make_archive('RPGBarServer','zip',root_dir='dist',base_dir='RPGBarServer')"
```

> 使用指南的源码保存在 `docs/使用指南.txt`（纳入版本管理），所以重复打包时不会丢。
>
> **打包坑**：`--clean` 在 `dist/` 文件数较多时会被安全删除守卫拦下，导致资源不刷新、打出旧包。
> 稳妥做法是先手动清空 `dist/RPGBarServer` 与 `build/` 再打包，打完用 grep 核对包内的新代码特征。

### 10.2 朋友怎么用

1. 解压 zip，双击 `RPGBarServer.exe`（首次可能需点「仍要运行」+ 防火墙「允许访问」）。
2. 黑色窗口里记下「局域网访问」地址（`http://192.168.x.x:8000`）。
3. 主机浏览器打开 `http://127.0.0.1:8000` 建房，把房号（5 位码）发给朋友。
4. 朋友浏览器打开「局域网访问」地址，填同一房号加入。
5. 想用大模型：各自点顶栏「⚙ 模型」接入（主机可配 DM，每个玩家可配自己的小助手）。

> 打包后的可写配置 `config.json` 放在 exe 旁边；只读资源（web/scripts/剧本）在 `_internal` 里。
> 异地联机需内网穿透（ZeroTier / Tailscale / cpolar / frp）。

### 10.3 玩家端小助手默认下沉本地（正式版）

通道已就位：把 `advisor` 槽位的默认值指向 `http://127.0.0.1:8080/v1`（玩家本机的 llama.cpp / Ollama），
算力就全在玩家机器上；主机玩家再额外给 `dm` 槽位接一个大模型。见 §7.2。

## 十二、已知局限（当前实现）

1. **游戏状态在内存中**：服务器重启即丢失房间与进度，未做持久化（后续可加 JSON/SQLite 存档）。这也意味着「中途加入」只在服务器不重启的前提下有效。
2. **未做鉴权/防滥用**：房间码公开可猜，无身份校验（demo 阶段可接受）。房主身份是「第一个加入的人」，不随连接恢复而转移。
3. **跨网络需自配穿透**：不同局域网的朋友联机需要 frp/cpolar 或云主机。
4. **回顾不含骰子细节**：新玩家能看到「做了什么」和「拿到了什么线索」，但不会重放此前的具体骰点；配了 LLM 时可由模型在旁白里概述。
5. **断线重连即视为中途加入**：玩家掉线后重新加入会走一遍补课流程（信息正确，只是会多出一段带入旁白）。
6. **Agent 已接模型，但当前剧本体量不大**：两个 Agent 的工具循环是完整实现，现阶段真实模型能发挥的空间主要在「自由发挥」的叙事上；换成更大、更细的剧本后价值更明显。
7. **模型设置存在浏览器本机**：换浏览器/清缓存后需要重填。想长期固化就写进 `config.json`（见 §7.2）。
8. **剧本接口只读 `scripts/` 目录**：这是安全取舍（服务端默认绑 `0.0.0.0`）。想用别处的文件就拷进 `scripts/`，或粘贴内容。
9. **「粘贴的剧本」不落盘**：通过 `content` 载入的剧本只存在于内存，服务器重启后回到配置文件指定的剧本。
10. **纯文本剧本是降级形态**：无结构文本无法表达出口/检定，引擎只能按切片顺序合成线性场景链（无分支、无线索、无检定）。要分支就写结构化 JSON。
